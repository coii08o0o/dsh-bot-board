## 2. 关键决策（含被推翻的需求）

### 2.1 用「三层」而不是「按状态分区」——推翻了使用者的原始选择

使用者原本选了「按状态分区」（像 Star Office UI 那样，状态决定角色走到哪个区域）。**没有照做**，理由：

分区解决的是「找得到」，但他的原话是「淹没在一片工位里、要挨个扫」——那是**看得见**的问题，是尺寸和对比度。搬完那盏灯还是 27px²，还得挨个辨形状。**搬完还得放大，不如直接放大。**

而且分区的代价是他自己在 0.3.x 攒下的资产（README 原话：「位置是你记人的方式」）。「等你」的出现与消失恰好是最频繁的事件，一个审批 30 秒内就可能被处理。

现在的方案：**位移只在「真的有 Bot 开始/结束一轮」时发生**——最低频、且本身承载信息（它走了 = 干完了）。颜色变了这种高频事件零位移。这才是 change blindness 的正确读法：不是位移都有害，是**与你关心之物无关的位移**有害。

### 2.2 `works.open > 0` 是「未清账」，不是「此刻被堵」

**这是本次最重要的语义红线。** `works` 来自 `state.json` 的派活记录，`open > 0` 只说明「还欠 N 项」，不说明「现在被堵住」——一个 Bot 可能一边欠 4 项一边正在飞快还账。把它画成「堵住」，用户会去催一个正在干活的人。

所以 `data-blocked` 由**接收方当前 scene** 决定（`handoffs.js`）：
- `alert` / `error` → `"true"`，加「被堵」
- `busy` / `waiting` → `"false"`，无强调
- `idle` / 未知 → `"idle"`，加「未开工」

真正的「此刻谁在等谁」在 `work.waiting[botId].bots` 活数据里。死锁（A→B 与 B→A 同时 open）标记用 `waiting` 算。

### 2.3 交接表放在工位网格**之前**

硬算：层 2 可用 269px（C4c 场景），6 个工位 2 行 = 268px。**交接表和 6 个工位不可能同时完整可见。**

而那一刻正是它最重要的时候——刚对班主任说完「八科都过一遍」，8 个在跑 + 8 条边同时存在。既然滚动不可避免，先看到关系：工位位置固定、有肌肉记忆，滚动看工位代价小；交接关系是新信息。头部 `N 项在交接` 负责完全不滚动时的回答。

有断言钉着（`render-check.mjs` 的 `the hand-off table comes before the workstation grid`）。

### 2.4 图例从常驻降级成抽屉

原来顶部那行 27px、六色、**每 tick 渲染、永不变化、位于视线第一落点**——首屏最贵的像素给了零信息。现在是一个 24px 的 `?` 按钮，点开走同一个 `.bb-drawer` 机制，零常驻像素。

### 2.5 层 1 不参与防抖（P0 的根因）

**踩过的坑，写在这里防止改回去。**

`useStableLayers` 原本对所有层归属加 1200ms 防抖，但 `Body` 里层 1 又按**实时** scene 过滤一次。两道过滤不同步，产生两个 100% 可复现的错误：

- 审批到来：t+1500 时头部显示「1 等你」，层 1 却显示「✓ 没有需要你的事」
- 审批被处理：t+1500 时那个 Bot **三层都不在**，9 个 Bot 数得出 8 个

触发条件恰好是「用户刚点完审批」。修法：层 1 用实时 `layerOf(row)` 分桶、`useStableLayers` 里对 `LAYER_ATTENTION` 直接 `map.delete`；层 2/3 用 `stable ?? live` 回落。

**两处修复是冗余不是互补**（单独回滚任一处都全绿），这是 P0 上故意的纵深防御，不要当成死代码删一处。

## 3. 还没做的事

### 3.1 只能真机验的三项

| 项 | 怎么验 | 判据 |
|---|---|---|
| **F2** 420×320 下 2 件需要你完整可见 | 打开 `docs/preview-0.4.1.html` 的 420×320 面板 | 算术 295.93 ≤ 320，余 24px；看实际有没有裁切 |

| **E3** chip 与行都可聚焦，Tab 会不会停两次 | 键盘走一遍层 1 | 同一个 44px 行里 Tab 停两次是新增的键盘噪音 |

### 3.2 必须靠真实布局引擎确认的一个数字

**560×480 / 3 件需要你 / 6 个在动**：算术 `39+132+6+10+256+8+4+24 = 479 ≤ 480`，**余 1.14px**。这是整版高度算术的成败点。预览里有这一张（标 `560×480 · C4c`），专门量有没有滚动条。

### 3.3 明确不做的（v0.5 候选）

- **看板内的审批/回答按钮**：这是「需要你」真正的终点，也最诱人，但要求向上游 POST，越过只读红线。**记入 v0.5。**
- 历史回放 / 时间轴：上游在子任务完成时删子记录，历史结构性不可得；要历史就得写状态。
- 节点连线图：420px 宽里连线会穿格子、跨滚动。分组边表能回答同一个问题（谁是瓶颈 = 谁的组最大）。
- 群聊面板：`rooms[].log[]` 无时间字段，本机 0 使用率。
- 累计统计（「今日完成 12 项」）：数据源不支持，会撒谎。
- 主题适配：奶油色 `#FAF7F1` 是刻意的浅色岛，不是漏改。

## 4. 改之前必须知道的陷阱

1. **`buildRows` 的排序一个字都不能改**。`render-check.mjs` 的「workstations never move」靠它。分层只在渲染期对 `rows` 做 filter。
2. **`Station` 的 memo 比较器按字段比较，不按对象身份**。1.5s 轮询每次重建行对象，按身份比较会让 9 个 SVG 每 tick 全量重绘。现在比较器含 `compact` 和 `onOpen`。
3. **`style.js` 从 `const.js` 插值那 6 个常量**（`ATTENTION_ROW_H` / `ATTENTION_GAP` / `IDLE_ROW_H` / `RUNNING_CELL_W` / `RUN_GRID_GAP` / `RUN_PAD_B`）。**不要再手抄数字**——CSS 是第二份手抄的数字时，高度断言就成了「常量对常量」的假绿。
4. **改任何 padding / gap / 行高都要重算 C4a/b/c**，三条断言在 `smoke.mjs`：
   - C4a 最坏（3 件需要你）= 307 ≤ 320
   - C4b 常见（2 件 + 1 行工位）= 296 ≤ 320
   - C4c 默认（3 件 + 6 个在动）= 479 ≤ 480
5. **层 1 必须实时，层 2/3 防抖**。见 §2.5，这是已经修过的 P0。
6. **`data-blocked` 读实时 scene，不读 works**。见 §2.2。
7. **`react-shim.mjs` 的 `useRef` 现在按 `(组件, hook 序号)` 持久**，`mount(type, props)` 把组件当元素挂载。直接调用组件（`render(Board({t}))`）会让 refs 写进上一个渲染过的组件的 store。新写测试用 `mount`。
8. **只读定位**：不写任何上游文件、不传 `locale`（上游是全局 `uiLocale`，会改新建 Bot 的招呼语言）、不加写操作。
9. **`react` / `react-dom` 构建期保持 external**，打进 bundle 会产生第二份 React，hooks 直接报错。
10. **改完必须 `npm run build`**，`client.js` 是构建产物，手改无效。
11. **桌面端改完插件要整个退出重开**：`killall -9 "DeepSeek Harness"`，`osascript quit` 会触发系统自动化权限弹窗。
