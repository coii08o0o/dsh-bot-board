# dsh-bot-board v0.4.0 需求摘要

- 对象：`dsh-bot-board` 仓库（v0.3.4 → 0.4.0）
- 依据：README、`src/client/{const,scene,rows,station,handoffs,panel,drawer,poll,style}.js`、`src/host/index.js`、`tools/{smoke,render-check}.mjs`、三条痛点的原始描述、四条收敛
- 原则：三条痛点和「按状态分区」这个方案都经过独立判断；四条收敛逐条判「同意 / 部分同意 / 反对」。**不为让结论好听而附和。**

---

## 0. 结论先说

1. 三条痛点里，**「看不清谁最急」和「看不到如何交接」是真痛点，且是同一个病**：面板把「需要你」的信息量压到了 27 平方像素（5.2×5.2 的状态灯）上，同时把「交接」压成了一行文字并埋在面板最底。**「视觉还能更有意思」是弱需求**，应排最后，且只能用承载信息的方式满足。
2. 「按状态分区」**和真正的痛点不匹配**。分区解决的是「找得到」，痛点是「看得见」；而分区要付的代价（位置记忆）恰好是 0.3.x 里刻意建立的资产。**存在一个不用付这个代价的方案。**
3. 四条收敛：D（重做注意力层级）**同意，且是四条里唯一真正的目标陈述**；B（视觉打折）**同意但缺一条正向预算**，否则会被执行成一张表格；C（只做当前拓扑）**方向对，但把「此刻」限定在 `works` 上是错的**——`works` 是「未清账」，不是「此刻」；A（两区）**部分同意：在一个方向上太保守，在另一个方向上太激进**。
4. 本次重做的**唯一硬指标**是：在 420×320 这个面板自己的最小尺寸下，一个人扫一眼能在不滚动的情况下看到「有没有事要我动手」。

---

## 1. 一句话目标

> **派完活之后，扫一眼就知道有没有事要我动手；没有的话，合上继续干别的，不用担心里面漏了什么。**

注意这句话有两个方向：**有事时能立刻看见**，和**没事时敢不看**。第二个方向现在完全没被设计过——面板永远用同样的音量说话，所以「没事」和「有事」看起来一样，只能一直看。这不是功能列表，这是这块面板存在的理由。

---

## 2. 为什么现在看不清（算术，不是审美）

这不是「设计不够精致」，是**像素预算分配错了**。按当前 CSS 计算（`style.js` 的 grid + `station.js` 的 viewBox 170×132）：

| 面板尺寸 | 网格列数 | 单个工位高度 | 可见完整工位 |
|---|---|---|---|
| 560×480（默认） | 3 | ≈176px | **6 / 9**（交接条出现时正好 6） |
| 420×320（最小） | 2 | ≈192px | **0 完整行 / 最多 2 个半工位** |

也就是说：**这块面板在自己的最小尺寸下，看不到任何一个完整的工位。** 「挨个扫一遍」这件事物理上做不到，要先滚动——而滚动会丢失全局视野，滚完就忘了前面看到谁红。

再看单个工位内部（173×176 ≈ 30,400 px²）：
- 真正区分六态的那个形状（状态灯）**只有 5.2×5.2 ≈ 27 px²**，占 0.09%。
- 显示器、眼睛、嘴加起来承载一点状态，约 1,000–1,400 px²，**≤5%**。
- 剩下 **95% 是椅子、桌子、桌腿、地影、道具**——九次刷新里一个像素都不会变。

结论：**这是一个用 95% 的面积重复「这是谁」，用 0.09% 的面积回答「要不要我管」的界面。** 「看不清谁最急」这句话，字面意思就是它。

> 这不是要拆掉教室。教室承担的是「这是谁」（身份），而身份**已经由名字标签和团子的脸各承担了一份**。教室的问题是它把「身份」画了三遍（位置、脸、名字），却没给「紧急度」留面积。

## 3. 核心场景

### S1 刚派完活（T+0 ～ 30 秒）
他给 Bot1 派完一轮活，派活记录开始出现，9 个 Bot 陆续动起来。

- **他要回答的问题**：① 活真的派出去了吗？② 有没有人一开始就卡住？
- **现在**：9 个工位陆续变绿，底部出现「Bot1 → Bot2 4 项待交」。他看不出**Bot2 接的是哪 4 项、还有谁接了**，因为列表最多 3 行（`handoffs.js:7` 的 `slice(0, 3)`）且按时间排序，不按人分组。有一个 Bot 一上来就报错时，那盏红灯会出现在 9 个同尺寸格子里的某一个——他要找。
- **判据**：30 秒内，他能不看会话就说出「几条边、共几项、谁接了、有没有人一上来就红」。

### S2 切回来（最高频，每几分钟一次）
他正在写东西，切回窗口，或者只是眼睛飘过去。

- **他要回答的问题**：**只看第一行——有没有事找我？** 没有就继续干别的。
- **现在**：第一行是静态图例（六个色块，永不变化，零信息），第二行开始才是 9 个同权重的工位。第一眼落在**最没信息量的东西上**。
- **这是本次重做最该赢的场景**：一个盯盘工具 90% 的价值在「没事的时候敢不看」。
- **判据**：一眼（< 1.5 秒，即一个轮询周期内）能得出「有事 / 没事」的二元结论；没事时面板的视觉音量显著低于有事时。

### S3 离开一小时回来
状态全变了。上游在子任务完成时会删掉子记录（README「已知边界」），**这一小时发生过什么，面板结构上不可能知道**。

- **他要回答的问题**：现在谁在跑、谁在等我、谁卡了。**不是**「这一小时干了多少」。
- **现在**：`done` 只有 7 秒就回落成 `idle`，所以「5 分钟前刚交活」和「闲了一小时」长得一模一样。3 分钟以上的报错已经降级成「闲着 + `!` 徽标」（0.3.4 已解决，是对的），但压缩层级时这个徽标**极易被丢掉**。
- **判据**：面板上不出现任何会让他误以为是「这一小时累计」的数字；失败徽标在任何压缩形态下都不丢失。

### S4（S2 的动作分支）需要你 → 点开 → 决定 → 切会话
- 顶部出现「Bot2 · 等你批 Bash · 2m12s」，点进去看命令原文（0.3.3/0.3.4 已解决），决定，跳会话。
- **判据**：从「看见」到「抽屉里看到命令原文」≤ 1 次点击；键盘 ≤ 2 次按键。

## 4. 必须解决的三件事

### 第一件：谁最急 —— 从「扫 9 个 27px 的灯」到「第一行就是答案」

| | |
|---|---|
| **现在什么体验** | 9 个同尺寸工位按名册固定排序（`rows.js` 的 `seatOrder`），紧急度只由一个 5.2×5.2 的形状灯编码。他必须做 9 次「找灯 → 辨形状 → 判状态」，且最小尺寸下有一半在滚动条外面。哪盏最该先管，面板不回答。 |
| **改成什么体验** | 面板最上方一个**条件渲染的「需要你」短列表**（0–3 行 + 溢出计数）。每行 = 团子小像（28–32px）+ 名字 + **动作原文**（`等你批 Bash` / `报错：模型超时`）+ 已跑时长 + 一个能看出形状的灯。顺序由一条**明确的纯函数规则**决定：`等你` 在 `卡住` 之前（一次点击就能恢复吞吐），同组内**等待最久的排最前**（时间戳升序，见 A1）。空时压成一行「没有需要你的事」。 |
| **怎么判断做成了** | ① 列表项集合 === 行里 `scene ∈ {alert, error}` 的集合，顺序由纯函数决定，可单测；② 420 宽下 3 项不需滚动（高度预算断言）；③ 全 idle 时该容器渲染为一行摘要而非 0 行（面板必须说「我查过了，没事」）；④ 任意状态变化后，网格内 9 个工位的相对顺序不变。 |

> **为什么是列表不是「紧急区」**：420px 宽下，一个完整工位 192px 高，一个列表行 44px。同样 3 个紧急 Bot，列表要 132px，工位区要 576px。**列表在这个宽度下是唯一能装下 3 个的东西。** 详见 §8-A。

### 第二件：交接 —— 从「一行字」到「谁压着多少、谁被谁堵住」

| | |
|---|---|
| **现在什么体验** | 底部一行 `Bot1 → Bot2　4 项待交　12 分钟前`，最多 3 条（`slice(0,3)`），按 `at` 倒序。看不到：Bot1**同时**压着 Bot2 4 项和 Bot4 3 项（两条独立记录，看不出合计）；看不到谁被谁堵住；看不到双向（A→B 与 B→A 同时开着，这是真正的死锁）；而且它躺在面板最底，视线最后到达。 |
| **改成什么体验** | **按发送方分组的有向边表**（不是节点连线图，见 §5）。每组一行头：`Bot1 · 共 7 项`，下面缩进的边：`→ Bot2 4 项 · 12 分钟前`、`→ Bot4 3 项 · 8 分钟前`。同一对出现双向时合成一行并标 `⇄ 互相等`。每条边可点进接收方抽屉。位置放在「正在跑」之内（它解释的就是正在跑的人），不放在面板最底。 |
| **怎么判断做成了** | ① 渲染出的边数 === `open > 0` 的记录数（≤ 上限），每个发送方分组的「共 N 项」=== 组内各边 `open` 之和（纯函数，可单测）；② 构造 A→B、B→A 同时 `open > 0` 的用例，必须出现「互相等」标记；③ 无 open 记录时整条不渲染；④ **边不撒谎**：接收方此刻在 `busy` 或 `alert` 时，该边不得使用「被堵」样式（`data-attr` 可断言）。 |

> **语义必须先定死**：`from → to` 是**派活方向**，而「欠账方向」是反的（`to` 欠 `from`）。今天这个箭头是歧义的——README 写「待交」，视觉读作「流过去」，两回事。重画之前必须二选一并写进文案，否则图画得越清楚，误导越强。

### 第三件：注意力层级 —— 从三层平铺到一条递减轴

| | |
|---|---|
| **现在什么体验** | 图例（静态 6 项，占首屏一整行 27px，**零信息量、永不变化**）→ 工位网格（9 个同权重）→ 交接列表（最底）。三层视觉重量几乎相同，眼睛没有落点。首屏最贵的像素给了最不需要看的东西。 |
| **改成什么体验** | 一条单调递减的轴：**需要你（0–3 行）→ 正在跑（整幅场景，含交接边）→ 闲着（压成一行名字）**。图例降级（不常驻）：六态的含义下沉到形状本身 + 抽屉，图例按需（hover / 首次）出现。头部计数改成先报「N 等你 · N 卡住」，`忙/等交活` 降为次要。 |
| **怎么判断做成了** | ① 从上到下第一个有内容的区块必须是「需要你」（其非空时）；② 9 个全闲时，主体区除一行摘要外无其他节点（渲染树断言）；③ 常驻图例节点消失后，六态仍可辨别（形状 + 抽屉文案断言）；④ 高度预算：三条分场景的常量断言 C4a/b/c 全绿（见 §9；原文那条单一不等式已被证明不可满足）。 |

> **一个顺带的、很便宜的发现**：`panel.js:373` 那行图例是六条不变量里唯一一条「每个 tick 都渲染、永远不变、且占最高价值位置」的节点。删掉它不需要改任何数据流，是本项目**单位成本最低的一次注意力改善**。但注意它会撞掉 `render-check.mjs` 的一条断言（见 §10）。

## 5. 明确不做

**边界不是谦虚，是防膨胀。以下每一条都有人会想做。**

1. **不做历史回放 / 时间轴 / 甘特图**。上游删记录，历史读不到；要历史就得写状态，违反只读。（详见 §8-C）
2. **不做节点连线图（node-link graph）**。420px 宽、2 列、可滚动的容器里，连线会穿格子、跨分区、被滚动裁切。分组边表能回答同一个问题，成本低一个数量级。
3. **不做看板内的审批 / 回答按钮**。这是「需要你」真正的终点，也是最诱人的一条——但它要求向上游 POST 审批动作，越过只读红线。**记入 v0.5 候选，本次不做。**
4. **不做 Star Office UI 式六区 / 自由走动 / 寻路 / 更多场景道具**。
5. **不加新的装饰性动画、新桌面道具、背景纹样、粒子**。现有 `bb-breathe / bb-blink / bb-tap / bb-wave / bb-note` 五条已够，且都要继续受 `prefers-reduced-motion` 约束。
6. **不做主题适配**。奶油色教室是刻意的浅色岛，`#FAF7F1` + 显式深墨 `#2C2C2A` 保留。
7. **不做群聊面板**（上游无时间字段，本机 0 使用率）。
8. **不做 9 → N 的泛化**。9 个固定，名册固定。
9. **不做移动端 / 触摸布局**。
10. **不改轮询节奏、不加第三个轮询器**。现有 1.5s / 6s（90s 尾部）/ 5s 三档是算过上游成本的，新层级不需要更多数据。
11. **不做任何累计统计**（「今日完成 12 项」「平均 4m」）。数据源不支持，会撒谎，且直接违反 S3。
12. **不做导出 / 分享 / 多实例**。

## 6. 约束

### 6.1 业务约束
- **9 个 Bot 固定**，名册顺序即网格顺序。
- **只读**：只读 `state.json` 与 `api/bot state`，不写任何文件、不改上游、**不传 `locale`**（上游是全局 `uiLocale`，会改新建 Bot 的招呼语言）。
- **面板尺寸**：默认 560×480，最小 420×320，最大 980×700。**560×480 是主用尺寸，420×320 是「必须仍然可用」的下限**——两者的判据不同，见下面这段。
  - **560×480（主用）**：三层全在，3 件需要你 + 6 个在动 + 闲着一行，零滚动（C4c = 479.31 ≤ 480，余 0.694px；浏览器实测余 0.72px）。这是默认打开、也是绝大多数时间停留的尺寸，所有「一眼看完」的判据都以它为准。
  - **420×320（下限）**：**层 1 完整可见**（3 行 = 148px + 头 39 + 闲着 24 + 边框 2 = 213px ≤ 320，剩 107px 给层 2），层 2 只保证**可见下限 96px**（整幅场景），有交接表时表在网格之前、先看关系；层 3 仍是一行。判据是「不滚动也能看到有没有事要我动手」，不是「三层全在」。
  - 为什么不是「420 是设计基准」：把最小尺寸当基准会把层 2 的两整行工位当成必须满足的目标，而它在 420×320 下物理上不可能（两行 266.31px > 层 2 能拿到的 107px），结果是所有断言只能靠缩格宽变绿——那会毁掉教室。反过来把 560 当基准、420 当下限，两边的断言都能各说各的真话。
- **奶油色是浅色岛**：房间内文字必须显式深墨，不能继承 shell 主题（暗色主题下会变成浅字浅底）。

### 6.2 三套检查必须保持全绿（`npm run check`）
现有断言**锁住**了以下不变量，重做时不能静默破坏：
- `smoke.mjs` CSS 段：`.bb-body` 必须同时有 `color:#2C2C2A` 与 `background:#FAF7F1`；`.bb-station-name` 显式深墨；四条 `step-end` 关键帧的百分比必须从 0% 严格递增；`.bb-blob` 的 `bb-breathe 2.6s`；`prefers-reduced-motion` 块必须排在**所有**关键帧与 `animation:` 规则之后；`.bb-station/.bb-handoff/.bb-btn/.bb-pill` 四条焦点环。
- `smoke.mjs` 产物段：bundle 只 `require('react')`；slot 注册在 `shell.overlay`、order 500；无 `dangerouslySetInnerHTML`；无 `locale: 'zh-CN'`。
- `smoke.mjs` locale 段：`zh` / `en` 键集**完全一致**（新增文案必须两边都加）。
- `render-check.mjs`：`buildRows` 输出必须保持名册顺序（**这条会被 §8-A 的方案保住，见 §10**）；`bb-handoff` 行必须有 `role="button"` + `tabIndex=0` + `onKeyDown`；抽屉 `aria-modal`、命令原文、选项、失败消息、时钟订阅。

### 6.3 实现约束（容易被忽略的三条）
- **`Station` 的 `memo` 按字段比较，不按对象身份**（`station.js:271`）。1.5s 轮询每次重建行对象，任何按身份比较的改动会让 9 个 SVG 每 tick 全量重绘。分组/分层**只能在渲染期对 `rows` 切片，不能改动行对象**。
- **键盘链路不能断**：新增的列表项必须是 `role="button"` + `tabIndex=0` + Enter/Space；抽屉的焦点陷阱（移入 / Tab 循环 / Esc / 关闭后回到原工位）必须继续成立——**新列表项打开抽屉后，焦点要回到那个列表项，不是回到网格**。
- **不新增第三方依赖**；`react` / `react-dom` 构建期保持 external。

## 7. 对三条痛点与「按状态分区」的独立判断

以下是对这三条痛点和「按状态分区」这个方案的独立判断，**其中一条与最初的选择不一致**。

### 痛点 1「看不清谁最急」——真痛点，但归因要改
- 成立，且是三条里最硬的一条。
- 但原因不是「没有分区」，是**没有排序 + 没有放大**：紧急度被压进 27px²，且散落在 9 个同权重格子里。
- **分区只是排序的一种实现方式，而且是较贵的那种**（它要求工位移动）。

### 痛点 2「看不到如何交接」——真痛点，而且比选项里那两条更值钱
- 成立。这条是提需求时自己补的，恰好指向一个结构性缺陷：**图被压成了线**（`handoffs.js` 每条 work 一行、最多 3 行、不分组、不合计），并且被埋在面板最底。
- 补充判断：这里藏着一个**没说但会立刻受益**的东西——`works` 里 A→B 与 B→A 同时 `open > 0`，或活数据里 `waiting[A].bots` 含 B 且 `waiting[B].bots` 含 A，就是**互相等死锁**。死锁在列表形态下永远看不见，在分组边表里是一行标记。这是本次重做能给出的、**最初提需求时没想到的**收益。

### 痛点 3「视觉还能更有意思」——弱需求，排最后
- **不是真痛点，是想要。** 理由：唯一使用者、每天扫几百次、常驻浮层。装饰性收益的边际曲线是「第一次最高，之后为负」；而每一帧新动画都是 1.5s 轮询周期上的重绘税。项目已经有 `prefers-reduced-motion`，说明这层被认真对待过。
- **可以满足的正确形态**：让**新结构**长在隐喻里（讲台前排队、任务单在工位间流转），而不是加动画。隐喻是这块面板的身份，不该丢；但它的增量应该来自「信息长成场景」，不是「场景加上动效」。
- **排序**：如果它和痛点 1、2 抢预算，它输。

### 「按状态分区」——**和痛点不匹配，不建议照做**

三条理由，从硬到软：

1. **它解决的不是那个问题。** 分区把「需要你」的工位搬到一块，解决「找得到」；原始描述是「容易被淹没在一片工位里，要挨个扫一遍才知道该管谁」——那是「看得见」，是**尺寸和对比度**问题。搬过去之后，那盏灯还是 27px²，还是要挨个辨形状。**搬完还得放大，那为什么不直接放大？**
2. **它要付的代价是 0.3.x 里刻意攒下的资产。** README 原话：「位置是你记人的方式」。分区意味着「等你」出现/消失时工位跨区移动，而「等你」的出现与消失恰好是最频繁的（一个审批 30 秒内就可能被处理）。**结果是失去位置记忆，换来一个仍然要逐项辨形状的列表。**
3. **存在一个不用付这个代价的方案**（§8-A）：把「需要你」做成网格**上方**的独立短列表，网格 9 个位置**永不移动**。同一份信息、同一处视线落点、零位移成本。**放弃「位置固定」这件事本身没错——但没必要放弃。**

> 一句话：**选的手段（分区）和目的（看得见）之间隔了一层。** 目的完全接受，手段建议换掉。如果仍要分区，请至少加上 §8-A 末尾的三条防抖约束。

## 8. 对四条收敛的判断

### A. 分区粒度从六区降到两区 —— **部分同意：一个方向太保守，另一个方向太激进**

**同意的部分**：六区是展示型产品的做法（Star Office UI 的六状态分区是为了「看着好玩」，不是为了「每 3 秒扫一次」）。这里是盯盘工具，位置随状态连续移动是纯噪音，change blindness 的判断成立。

**太激进的部分**：**「两区」仍然要动工位。** 两区只把位移频率降到 1/3，没有归零。而「需要你」的集合恰恰是变化最快的集合（审批出现 → 处理 → 消失，全程可能 30 秒）。为了一个每秒 1.5 次刷新的面板，付一个每 30 秒重排一次的代价，不划算。

**太保守的部分**：**它不敢动工位本身的信息密度。** 两区方案里，9 个工位还是 176px 高、95% 面积画桌椅。分区之后，「正在跑」那一区仍然是 6 个装不下的整幅场景。**真正的浪费不在「工位放在哪」，在「工位画了多大」。**

**我的建议（保留目标，换掉手段）**：
> **不是「把网格切成两区」，而是「按信息密度分三层，网格永不重排」。**
>
> - **层 1 需要你**：0–3 行紧凑列表（44px/行），条件渲染，空时一行摘要。
> - **层 2 正在跑**：整幅场景，**只放正在跑的 Bot**（典型 2–6 个），名册序。交接边表放在这一层内部（它解释的就是这些人）。
> - **层 3 闲着**：一行名字（+ `!` 徽标）。
>
> 这个方案的好处是**位移只在「真的有 Bot 开始/结束一轮」时发生**——那是最低频率、且**承载信息**的事件（它走了 = 它干完了，值得注意）。而「颜色变了」这种高频事件不产生任何位移。
>
> **这才是 change blindness 的正确读法**：不是「位移都有害」，是「**与我所关心之物无关的位移**有害」。

**如果他仍要两区，必须加三条约束**（否则会比现在更糟）：
1. 只有 `alert` / `error` 跨区，`busy` / `idle` / `waiting` / `done` 永不跨区。
2. 600ms 稳定期：状态在 600ms 内翻转不触发移动（防止一次 tick 抖动搬两次家）。
3. 跨区不做位移动画（瞬时切换 + 一个静态的「↑ 已上移」标记），动画会把噪音放大成事件。

**退化态警告**：两区在两端都不成立——9 个全 `alert` 时「需要你」区就是整个网格（层级消失）；9 个全 `idle` 时它是空的（布局跳一次）。分层方案同样需要处理，见 §9 的 A7。

---

### B. 「视觉更有意思」打折处理 —— **同意，但缺一条正向预算，否则会被执行成一张表格**

**同意**：常驻浮层的装饰性动画，第一次看收益最高，之后是纯干扰。这条判断对，而且和「每天扫几百次」的使用频率直接相关。

**但「只加承载信息的视觉」是一句否定式规则，无法执行。** 一条只说「不许」的规则，落到实现上会收敛到最保守的解：把教室拆成三张表。那样痛点 1、2 解决了，产品身份没了，而**身份正是这块面板值得天天开着的原因**——一块纯表格的浮层，没人会留着。

**补一条正向预算**（把「承载信息」变成可判定的）：
> **允许**：尺寸、字重、分组、缩进、计数、边界、底色层级——即**在同一个像素上多编码一层信息**的手段。
> **禁止**：新增 `@keyframes`、新增桌面道具、背景纹样、纯色编码（色盲）、任何「只为了好看」的装饰。
> **判据**：任何一处视觉改动，必须能回答「它编码了什么信息」。答不上来就砍。

按这条预算，本次可以放心花视觉预算的地方只有三处：① 层 1 的行内**动作原文**（文字是最高密度编码）；② 交接边的**分组缩进 + 计数**；③ 层 2 与层 3 之间的**尺寸落差**（这是「层级」本身）。三处都答得上「编码了什么」。

---

### C. 交接只做「当前拓扑」，不做历史回放 —— **方向同意，但把「此刻」限定在 `works` 上是错的**

**同意的部分**（而且理由比他更硬）：这不是设计取舍，是**约束**。上游在子任务完成时删掉子记录，历史链路结构性不可得；想要历史就得写状态，越过只读红线。所以「不做历史」不需要论证，它是前提。

**反对的部分**：`works` **不是「此刻」**，它是「**未清账**」。

- `works` 来自 `state.json` 的派活记录，`open > 0` 只说明「还有 N 项没交回来」，不说明「现在被堵住」。一个 Bot 可能一边欠着 4 项、一边正在飞快地跑（那 4 项正在被处理）。
- 真正的「此刻谁被谁卡住」在**活数据**里：`work.waiting[botId].bots`（这个 Bot 在等哪些 Bot）。1.5 秒刷新，是当下的事实。
- 两者混为一谈，画出来的图会**撒谎**：把「欠账」画成「堵住」，用户会去催一个正在干活的人。

**修正建议**：
> 分两层，且**在视觉上必须可区分**：
> - **欠账（`works`）**：谁压着多少、往哪流 —— 分组边表，容错陈旧。
> - **堵住（`waiting`，活）**：此刻谁在等谁 —— 只画真正被堵的边，且**只有这一层能做环检测**（A 等 B 且 B 等 A = 死锁）。
>
> 最小可行版：边表只用 `works` 画（回答「谁压着多少」），**但一条边的接收方当前在 `busy`/`alert` 时，禁止使用「被堵」样式**；死锁标记用 `waiting` 的活数据算。这样既不撒谎，也不引入第二套数据源。

**另外，「拓扑」的形态应该是分组边表，不是节点连线图。** 9 个节点在 420px 宽里画连线，必然穿格子、跨滚动、跨分层；而分组边表能回答同一个问题（谁是瓶颈 = 谁的组最大），成本低一个数量级。**「看不到完整关系」的解法是「聚合 + 分组」，不是「连线」。**

---

### D. 重做的不是皮，是注意力层级 —— **同意，这是四条里唯一真正的目标陈述**

前三条都是手段，只有这条是目标。「从上到下按『我要不要动手』递减」是一个可执行、可验证、且能推导出前三条的设计原则。

**补两条它自己没推出来的推论**：

1. **图例必须降级。** 层级重做的第一件事就是把首屏最贵的像素从「永不变化的六个色块」手里拿回来。`panel.js:373` 那行图例占 27px 高度、位于视线第一落点、每 tick 渲染、零信息。它现在是「图例 → 网格 → 交接」三层平铺里最上面那层——**层级重做却留着它，等于没做**。
2. **必须给出退化规则。** 「闲着压成一行」在两端都失效：
   - **9 个全闲**：主体只剩一行——这是**特性**（面板安静了），但要保证它说的是「我查过了，没事」，不是空白。
   - **9 个全 `alert`**：如果全是紧急，紧急就无意义。层 1 必须有上限（3 行）+ 溢出计数（`还有 6 个`），且**溢出不能丢信息**——至少保留「N 等你 · N 卡住」的计数在头部。
3. **压缩不得丢徽标。** `0.3.4` 把红灯收窄成「只表示现在」，超过 3 分钟降级成「闲着 + `!`」。层 3 压成一行名字时，`!` 必须跟着名字走，否则这条 0.3.4 的成果在重做里被静默回退了。

## 9. 验收标准

**本节共 23 条可测验收**：A1–A4（4）/ B1–B5（5）/ C1–C5（5）/ D1–D3（3）/ E1–E3（3）/ F1–F3（3）。C4 是一条（内部由 C4a/C4b/C4c 三条断言实现，计数仍算 1）。

标注：**【smoke】** = 可在 `tools/smoke.mjs` 用纯函数断言；**【render】** = 可在 `tools/render-check.mjs` 走渲染树断言；**【人工】** = 需要真机看，但给出可核对的判据。

> **诚实声明**：检查环境没有布局引擎（`react-shim` 只渲染树，不排版）。所以「不用滚动」这类判据我用**高度预算常量**近似，并在注释里写明它是预算断言而非实测布局。这比写一条测不了的「看起来更清楚」强。

### 结构与顺序
- **A1【smoke】** `attentionOf(rows)` 的返回集合恒等于 `rows.filter(r => r.scene === 'alert' || r.scene === 'error')`；顺序满足：所有 `alert` 在 `error` 之前，同组内按 `waitSince`（`approvalAt || since || failureAt`）**升序——等待最久的排最前**。构造 9 条用例覆盖两两组合。
- **A2【smoke】** 对同一组 Bot，任意改变 `activity` / `waiting` / `approvals` / `errors`，`buildRows` 输出的**名字序列恒等于名册顺序**（这条保住 `render-check:81` 现有断言）。
- **A3【smoke】** `attentionOf` 结果长度 > 3 时，返回 `{ items: 前 3, overflow: n - 3 }`，且 `items.length + overflow === n`（不丢计数）。
- **A4【smoke】** 全 idle 快照下 `attentionOf` 返回空数组，且面板渲染的层 1 为**一行摘要节点**（非 `null`）。

### 交接
- **B1【smoke】** `topologyOf(works)` 的边数 === `works.filter(w => w.open > 0).length`（≤ 上限时）；每个发送方分组的 `total` === 组内 `open` 之和。
- **B2【smoke】** 构造 `A→B open 4` + `B→A open 3`，输出必须含一条 `mutual: true` 的合并项，且 `total` 为两侧之和或两侧分别可见（语义二选一，但必须显式）。
- **B3【smoke】** `works` 全为 `open === 0` 时 `topologyOf` 返回空，面板不渲染该区。
- **B4【render】** 接收方当前 `scene === 'busy'` 时，该边的节点**不带** `data-blocked="true"`（防止把欠账画成堵住）。
- **B5【render】** 每条边是 `role="button"` + `tabIndex=0` + `onKeyDown`，Enter/Space 打开接收方抽屉（沿用现有 `bb-handoff` 类名，保住现有断言）。

### 注意力层级
- **C1【render】** 层 1 非空时，它是面板主体中**第一个含文本内容的区块**（按树顺序断言）。
- **C2【render】** 常驻图例节点不再出现在默认渲染中；六态仍可辨别——`.bb-lg-*` 的形状样式或抽屉文案仍覆盖六个状态名（替代现有 `render-check` 的图例断言，不能只是删掉）。
- **C3【render】** 9 个全 idle 时，主体区节点数 ≤ 2（一行摘要 + 无网格）；9 个全 busy 时，层 3 不渲染。
- **C4【smoke】** 高度预算常量，由下面三条替代（原式见下方说明，**数学上不可满足，已作废**）：
  - **C4a** `PANEL_BORDER + HEAD_H + 3*ROW + 2*GAP + ATT_PAD_V + IDLE_ROW_H + RUNNING_MIN_H ≤ 320` = **309 ≤ 320**（3 件需要你 + 层 2 可见下限）。
  - **C4b** `PANEL_BORDER + HEAD_H + 2*ROW + GAP + ATT_PAD_V + RUNNING_CELL_H + RUN_PAD_B + IDLE_ROW_H ≤ 320` = **298 ≤ 320**（2 件需要你 + 一整行工位）。
  - **C4c** `PANEL_BORDER + HEAD_H + 3*ROW + 2*GAP + ATT_PAD_V + 2*cellHeight() + RUN_GRID_GAP + RUN_PAD_B + IDLE_ROW_H ≤ 480` = **479.31 ≤ 480**（默认尺寸，3 件需要你 + 6 个在动）。
  - 三条都必须在断言标签里注明「预算，非实测」，且都显式含 `PANEL_BORDER = 2`。

  > **原 C4 为什么作废**：原文是 `HEAD_H + ATTENTION_ROW_H*3 + RUNNING_CELL_H*2 ≤ 320`，即 `39 + 148 + 2×格高 ≤ 320` → `格高 ≤ 66.5` → 格宽 60px（格高 = 0.7765W + 20）。60px 的工位里灯只有 1.84px、眼镜描边 0.71px、屏幕进度条 1.06px——那不是「小一点」，是缩略图。反过来，要让灯守住 4px 轮廓下限需要格宽 ≥106 → 格高 ≥103 → 两行 206 → `39 + 148 + 206 = 393 > 320`。**两个方向都不成立，所以这条不等式不是「暂时没过」，而是永远红着**；一条永远红的断言最终只会被注释掉，那比没有断言更糟。换成三条对应真实场景的可满足断言，是把它从「不可能」改成「三个都必须真」。
- **C5【smoke】** `prefers-reduced-motion` 块仍在最后一个关键帧与最后一条 `animation:` 之后；新增样式不得引入未受该块覆盖的动画。

### 语义与不撒谎
- **D1【render】** 压缩到层 3 的 Bot 若 `badge === true`，其名字旁必须存在 `bb-badge` 节点。
- **D2【人工】** 面板上不存在任何「累计 / 今日 / 平均 / 已完成 N 项」形态的数字（逐项核对文案）。
- **D3【smoke】** 新增 i18n 键在 `zh` / `en` 中键集完全一致（现有断言自动覆盖）。

### 键盘与可达性
- **E1【render】** 层 1 的每一行 `role="button"` + `tabIndex=0` + `onKeyDown`。
- **E2【smoke】** `.bb-attention`（或等价类名）出现在焦点环规则的选择器列表里。
- **E3【人工】** 键盘：Tab 进入层 1 → Enter 开抽屉 → Esc 关闭 → **焦点回到刚才那一行**（不是回到网格）；抽屉打开时 Tab 不逃逸。

### 回归底线
- **F1** `npm run check` 全绿（build + smoke + render），且 §6.2 列出的每一条现有不变量仍在。
- **F2【人工】** 420×320 下，层 1 有 2 项时，两项都完整可见且不需滚动（用真机核对，作为 C4b 预算的最终验证）。
- **F3【人工】** 静置 60 秒（全队闲着）时，面板不产生任何视觉变化（无跳动、无重排、无闪烁）——这条是「盯盘工具」的底线，比任何新增都重要。

| G5【smoke】 | `attentionOf` 在**名额 ≥ 2** 时保留最老的 error | 3 个 alert + 1 个老 error → `items.some(r => r.scene === 'error')` | 成立（`layers.js:72-75`）。名额为 1 时不保留：一条 44px 行只能装一个答案 |
| G6【smoke】 | `waitSince` 取**审批到达时刻**，不是本轮开始时刻 | `waitSince === approvalAt \|\| since \|\| failureAt`；构造「12 分钟的一轮 + 3 秒前的审批」，`waitSince` 必须是 3 秒前 | 成立（`rows.js:175`）。用 `since` 会把 3 秒的等待读成 12m34s |
| G7【smoke】 | 产物 banner 带 **src 指纹**，且能被独立重算 | `npm run verify` 比较 banner 里的戳与现算指纹 | 成立（`tools/verify-artifact.mjs`）。没有它时，把旧 `client.js` 放回 HEAD 再跑 smoke + render-check 仍然 378 条全绿 |

为什么 G1 和 G7 是本轮最值钱的两条：它们防的不是「算错」，而是**「算错了也没人发现」**——一个是把预算调到 600 仍然绿（`IDLE_BUDGET` 原本是个裸的 380，没有上界），一个是产物过期仍然绿（`npm run check` 永远先 build，所以「过期」这个状态根本无法表达）。

## 附：本次一句话取舍

**如果只能做一件事，做「需要你」的短列表（第一件事）。** 它单独就能消掉最硬的痛点，且不改任何数据流、不动 `buildRows`、不破任何现有断言。
**如果只能做两件，加交接分组边表（第二件）。**
**第三件（注意力层级）是把前两件组织成一条轴——它是前两件的容器，不是第三个功能。**
**「视觉更有意思」排最后，且只准用「同一像素多编码一层信息」的方式实现。**
