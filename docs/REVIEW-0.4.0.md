### 2.1 哲学：那条支撑论证是反的

需求 §8-A 用这条否决了「两区」方案：

> 位移只在「真的有 Bot 开始/结束一轮」时发生——**那是最低频率**的事件。而「颜色变了」这种高频事件不产生任何位移。

但 `layers.js:19-24` 把层边界划在 `idle ↔ busy` 上，而 **idle↔busy 是整个六态里频率最高的转移**（每一个 turn 的两端）。审批的出现/消失（两区方案会移动的那条边界）在健康团队里远比 turn 循环稀疏。

后果可量化：560 宽下 4 个在动 → 3+1 两行（第二行居中 1 个）；其中一个结束 → 3 个在动 → 一行 3 个居中。**整幅教室上移 143px 并横向重排。** 这不是「最低频率」，这是每个 turn 一次。

设计仍然是好的——位移**承载信息**（有人走了 = 他干完了），这是它成立的真实理由。但需求里写的那个理由不成立，而它恰好是用来否决替代方案的那一条。**请把论证换成「位移承载信息」，不要留「最低频率」这句。**

同时：主张号称「一条轴」，实际是**两条**——层 1 是注意力（要不要动手），层 2/3 是活跃度（在不在动）。`waiting`（等另一个 Bot 交活）和 `done` 都不需要用户动手，所以它们和层 3 在「要不要我管」上是同一档。这个两段式是**对的**（在跑的人值得一张画），但描述要诚实。

### 4.3 高度实算（按 `style.js` 反推，不是抄常量）

```
工位格实高 = 148×(132/170) + (18+1) + 1 = 114.92 + 19 + 1 = 134.92px
const.js:29  RUNNING_CELL_H = 134        → 差 0.92px
```

| 断言 | 算式（含 CSS 里被漏掉的项） | 实算 | 预算 | 判定 |
|---|---|---|---|---|
| C4a 3 件需要你 + 在动可见下限 | `39+148+24` = 211，在动得 109 | 109 ≥ 96 | 320 | ✓ 余 13 |
| **C4a+ 3 件 + `还有N个`** | 多一行 = `3(gap) + 17.5(11px×1.5+1px)` = 20.5 | 在动只剩 **88.5** | 320 | **✗ `RUNNING_MIN_H=96` 被破 7.5px** |
| C4b 2 件 + 一行整工位 | `39+101+24` = 164，需 `134.92+4` = 138.9 | 156 ≥ 138.9 | 320 | ✓ 余 17 |
| **C4c 3 件 + 两整行（560×480）** | `39+148+24` = 211，需 `2×134.92 + 8(gap) + 4(.bb-run 下内边距)` = **281.8** | 只有 269 | 480 | **✗ 超 12.8px** |

**C4c 是一条绿着的假话。** 设计文档 §8.2 写「269px（正好两整行，余 1px）」，但 269 里没扣 grid gap 和 `.bb-run` 的下内边距；`smoke.mjs:364` 只加了 `2*RUNNING_CELL_H`。真实情况：**560×480、3 件需要你、6 个在动 → 第二行工位的名字被裁 13px 且出现滚动条。** 「默认尺寸下不用滚」这个卖点是假的。

根因在 §8.3 的推导：`2×格高 ≤ 480-39-148-24 = 269 → 格高 ≤ 134.5`，这 269 里同样没扣 gap+padding，所以「148 是唯一整数解区间上界」这个结论也不成立——真上界是 `2×(0.776W+20)+12 ≤ 269 → W ≤ 139.8`。

**4 件以上时层 2 实得 88.5px 是什么样**：可见 84.5/115 的场景 → viewBox y 到 97。桌面（y=88）在，团子脸在，**名字行整行不见**。所以 `RUNNING_MIN_H` 这个常量（「团子脸 + 桌面」）被破了，但它想保的东西还在。这决定了 §5 第 1 条的裁决。

### 4.5 死锁：**成立，且「两侧各留一条」是对的**

`A→B open 4` + `B→A open 3`，两侧都 busy：

```
班主任 共 4 项 / ⇄数学 4 项待交 互相等 1 分钟前
数学   共 3 项 / ⇄班主任 3 项待交 互相等 1 分钟前
```

`data-mutual="true"` 两侧都有（2 条），`⇄` 与「互相等」同时出现，`data-blocked` 都是 `false`（不撒谎）。

**合并成一条是错的**，理由比实现者写的更硬：合并后必须选一个方向的计数显示，而**组头 `共 N 项` 是整张表的答案（谁是瓶颈）**。合并会让「班主任压着 7 项」或「数学压着 3 项」之一消失，也就是让瓶颈消失。多一行换瓶颈不消失，值。

唯一小瑕疵：`⇄` 取代 `→` 后**方向在这个 row 内部丢失**，只能靠组头推。可接受（组头就在上面一行）。

### 4.6 新发现（P0）：面板会自相矛盾，且发生在最该准的那一刻

`panel.js:99-133` 的 `useStableLayers` 对**所有**层归属加 1200ms 防抖，`panel.js:139-150` 按防抖后的层分桶，然后 `panel.js:158` 的 `attentionOf(hot)` 又**按实时 scene 过滤一次**。两道过滤不同步。

项目自带的 `react-shim` 每次渲染重建 `useRef`（`react-shim.mjs:22`），所以防抖在测试里从不生效——**这个 bug 结构上不可能被现有断言发现**。我用一个 ref 持久的 hook runtime 复现（`/tmp/bb-review`，工作区未动）：

**CASE A · 审批到来（idle → alert）**

```
t+0     L1rows=0  L1="✓没有需要你的事"   L2=0   L3="闲着Chief Researcher 班主任…"   | 实时: 0 alert
t+1500  L1rows=0  L1="✓没有需要你的事"   L2=0   L3="闲着Chief Researcher 班主任…"   | 实时: 1 alert  ← 矛盾
t+3000  L1rows=1  L1="Researcher 等你批 Bash"                              | 实时: 1 alert
```

t+1500 这一刻：**头部（`panel.js:304-308` 用实时 rows）显示「1 等你」，正下方层 1 显示「✓ 没有需要你的事」，而那个 Bot 还在「闲着」那一行里。** 面板在同一屏里说了两句相反的话。

**CASE B · 审批被处理（alert → busy）**

```
t+0     L1rows=1  L1="Researcher 等你批 Bash"   L2=0   L3="闲着Chief 班主任…(8 人)"
t+1500  L1rows=0  L1="✓没有需要你的事"          L2=0   L3="闲着Chief 班主任…(8 人)"  ← 人不见了
t+3000  L1rows=0  L1="✓没有需要你的事"          L2=1   L3="闲着Chief 班主任…(8 人)"
```

t+1500 这一刻：Researcher **既不在层 1、也不在层 2、也不在层 3**。9 个 Bot 的面板里数得出 8 个。原因：防抖层说 `ATTENTION`（所以进 `hot`），`attentionOf` 按实时 scene（busy）把它滤掉，于是三层都不要它。

**为什么这是 P0 而不是 P1**：它 100% 可复现（不是竞态）；触发条件是**用户刚点完审批**（他此刻一定在看这块面板）；错误方向是「面板说没事，其实有事」——和团队自己定的红线（「不能把欠账画成堵住，用户会去催一个正在干活的人」）属于同一类错误，只是反方向；而且它同时让**层 1 与头部计数互相矛盾**，一块自相矛盾的面板比一块不精确的面板更坏。

**修复**（`panel.js:99-150`，约 8 行）：

```js
// useStableLayers：只防抖「在动/闲着」这条边界。「需要你」不记忆、不防抖——
// 它是这块面板唯一不许滞后的答案；防抖它会让面板和自己的头部打起来。
function useStableLayers(rows) {
  ...
  for (const row of rows) {
    const id = row.bot.id
    const live = layerOf(row)
    if (live === LAYER_ATTENTION) { map.delete(id); continue }   // ← 新增
    const target = live                                          // 只剩 RUNNING / IDLE
    ...（其余不动）
  }
}

// Body：按实时 scene 分「需要你」，按防抖层分「在动/闲着」，离开层 1 时回落实时
for (const row of rows) {
  const live = layerOf(row)
  if (live === LAYER_ATTENTION) { hot.push(row); continue }      // ← 实时，不过防抖
  const stable = layers.get(row.bot.id)?.layer
  const bucket = (stable === LAYER_RUNNING || stable === LAYER_IDLE) ? stable : live
  ;(bucket === LAYER_RUNNING ? moving : resting).push(row)        // ← 回落，不再"三层都不要"
}
```

防抖想防的那件事（一次 tick 的抖动不让工位搬家）**完好保留**：idle↔busy 仍然过 1200ms 窗口。被去掉的只是「让最重要的那一行也延迟」这个副作用。

### 4.7 其余新发现

- **P1 · 4 件以上「需要你」的人在整个面板里不存在。** 6 个审批时：层 1 渲染 3 行 + `还有 3 个`，而 `还有 3 个` 是个**没有 role / tabIndex / onClick 的 div**（`attention.js:61-63`，实测 props 只有 `className` 和 `children`）。物理/化学/生物 三个名字**在面板任何位置都不出现**（实测 `textOf(body).includes('物理') === false`），也点不开抽屉。对比层 3 的 `+N`：有 `role="button"` + `tabIndex=0` + Enter/Space + 焦点环（`attention.js:96-106`）。**同一类溢出，两层待遇不同，而层 1 是更重要的那层。** 需求 §4 A3 只要求「保留计数」，但一个点名了 9 个角色、每个角色都能点开抽屉的面板，把 3 个人藏到无名无姓，越过了「不丢信息」的底线。
- **P2 · `Station` memo 不比 `compact`**（`station.js:337-351`）。当前安全（只有层 2 传 `true`，实例 `key` 是 `row.bot.id` 且从不切换）。顺带：也不比 `onOpen`，目前靠 `openDrawer` 是 `useCallback([])` 稳定。
- **P2 · 层 1 时长列是 `row.since`（`attention.js:59`）。** 对 `error` 且这一轮从未开始（`since === 0`）的行，`Elapsed` 返回 `null`，**时长列空着**——而 `row.failureAt` 就在行上，`attentionOf` 也已经拿它排序。一行改：`since: row.since || row.failureAt`。另外对 `alert`，这列显示的是**这一轮的时长**，不是**审批等了多久**（审批没有自己的时间戳），会把等待时间说长。方向安全（宁长不短），但要写进注释。
- **P2 · `rows.js` 的裁剪预算和层 1 的列宽对不上。** `PHRASE = 16` 与 204px（≈16 个中文字）吻合，但 `clip(question.question, 20)`（`rows.js:50`）和 `clip(failure.message, 22)`（`rows.js:65`）都超。也就是说**填满层 1 的两个状态（question / error）永远会被裁**，省略号落在句子中间。设计文档 §3.3「裁剪预算和布局预算刚好吻合」只对 16 那条成立。抽屉有全文，所以不致命。
- **P2 · 僵尸断言。** `render-check.mjs:320` 标签写「the legend carries the new waiting state」，但图例已经不在 `Board` 里了；它现在靠头部的 `0 等你 / 0 等交活` 通过。**断言绿着，但测的不是它说的东西。**
- **P2 · 1 件需要你时层级补偿最弱。** 3 行时有 44px 节律 + 3 个灯的竖轨；1 行时节律没了、竖轨只有一个点，只剩一条 3px 彩条撑着一块 1.07:1 的白卡。而「1 件」是最常见的形态。补偿「够用」但不「够响」——用户的抱怨原话是「看不清谁最急」，响度是他的原话。

## 5. 四条遗留的裁决

### 1. `.bb-att-more` 不在 C4a 预算里 —— **部分同意主理人：接受现状，但数字错了，且他提的 C4d 会红**

- 实测代价不是「约 16px」而是 **20.5px**（gap 3 + 11px×1.5 + 1px padding），因为 `.bb-att-more` 是 `.bb-attention` 的第 4 个子节点，要吃一个 3px gap。
- 层 2 因此从 109 → **88.5px**，比 `RUNNING_MIN_H = 96` **低 7.5px**。所以主理人提的 C4d（`… + MORE + RUNNING_MIN_H ≤ 320`）= 328 > 320，**写出来就是红的**。「接受现状 + 加断言」这两件事不能同时成立。
- 但常量被破 ≠ 目的被破：88.5px 下仍能看到团子脸和桌面（viewBox 到 y=97），只丢名字行。
- **我的裁决**：接受，但必须选一条落地，不能含糊：
  - **(a) 推荐** 把 `.bb-att-more` 做成**第 3 行内的右对齐尾随 chip**（`flex:1` 的动作列有 204px，塞一个「还有 3 个」够）。高度代价 **0px**，同时顺手修掉 §4.7 的 P1（它变成可点的展开器）。C4a 保持绿，不用新增常量。
  - **(b) 次选** 把 `RUNNING_MIN_H` 降到 88，并在注释里写清「4 件以上时名字行被裁，桌面保底」，C4d 用 88 重写。
  - **(c) 不要** 就这么接受而不加任何断言——那等于把「4 件以上会怎样」交给下一个人猜。

### 2. 层 2 的动作从常显变 hover —— **同意主理人，但要修正一处损失归属**

- 不是「只剩 hover」，是**只剩 `title`**（`station.js:282, 287`）。好处：`role="button"` + `title` 让无障碍名仍含动作，读屏拿得到；抽屉 1 次点击 / 2 次按键。
- **但损失不在 `busy`，在 `waiting`。** `busy` 的动作是「调用 Bash」，确实次要。`waiting` 的动作是「等 Chief」——**这条恰恰是决策相关的**（链条卡在谁身上）。而交接边表是 `works` 派生的**欠账**，不是 `waiting` 派生的**实时堵点**。所以「物理在等谁」现在只能点开看。
- 设计别处花了一整条论证说 `waiting` 必须是独立状态因为「链条在转」——**能转的链条看不见，这个状态的价值就打折了。**
- **裁决：接受**（134px 的代价是真金白银，且 §11.19 禁止给边加标记）。**但要加一条断言把这个出口钉住**：compact 工位的 `title` 必须包含动作原文。否则下一个人删掉 `title` 里的 `${action}` 也没人知道。

### 3. `Station` memo 不比 `compact` —— **同意主理人，无条件**

一行 `&& prev.compact === next.compact`，成本可忽略，修的是一个「将来某人让同一实例切 compact 会拿到旧渲染」的隐患。顺手把 `prev.onOpen === next.onOpen` 也加上，理由相同（现在靠 `useCallback([])` 侥幸稳定，不是靠契约）。

### 4. 没法真机看，计划导出静态 HTML —— **同意，但要说清它关掉了什么、没关掉什么**

- **关得掉**：44px 行里 30px 头像是否局促、5.57px 灯是否可辨、420 下头部是否裁掉 `最久`、560×480 下第二行工位是否被裁 13px。这些都需要**布局引擎**，而浏览器打开静态 HTML 就有布局引擎。**所以这个计划是有实质作用的，不是安慰剂。**
- **关不掉**：第一落点到底落在层 1 还是层 2 的团子上（§2 的层次扣分点）。这个只能靠人眼/眼动，静态导出测不了。
- **两个附加要求**，否则导出会变成一张漂亮截图：
  1. 必须带 **420×320 / 560×480 两个固定视口**，且 420 是默认视图（它是设计基准，不是降级态）。
  2. 必须渲染**退化态**，不是 happy path：9 个全 alert、4 件以上 + 溢出、全 idle、A↔B 互相等、接收方 busy 的边。只导出「3 个需要你 + 2 个在动」等于什么都没验。
- **还有一条前置**：先把 §4.3 的 C4c 算对。否则导出会显示一条 13px 的滚动条，团队会以为是导出环境的问题，而不是预算的问题。

## 6. 真的解决了「看不清谁最急」吗？

**解决了，而且不是量级变化。但只解决了这一件事，且当前实现会在这件事上撒谎 1.5 秒。**

先按动作数算。用户从「切回窗口」到「得出有没有事找我」：

**旧版（v0.3.4，420×320）**

| 步 | 动作 | 成本 |
|---|---|---|
| 0 | 第一落点落在 27px 常驻图例（6 个永不变化的色块） | 1 次注视，信息量 **0** |
| 1 | 移到网格。420 下 2 列 ×192px 格，视口约 250px → **0 个完整工位可见** | 必须滚动，而滚动丢全局视野 |
| 2 | 滚 4 次才扫完 9 个 | 4 次手势 + 4 次重新定位 |
| 3 | 每格找那盏 5.2×5.2 的灯（占格子 0.09%），辨形状，映射到状态，再映射到「我要不要动手」 | **9 次**「找 → 辨 → 映射」 |
| 4 | 找到红/黄之后读 11px 的动作 | N 次 |

合计 **≈14–18 步**，且第 1 步就注定了「不滚动做不到」——不是慢，是**物理上不可能**。

**新版（3 件需要你，420×320）**

| 步 | 动作 | 成本 |
|---|---|---|
| 0 | 第一落点是主体区第一块内容 = 第一张白卡：3px 彩条 + 30px 脸 + 600 名 + 12px 句子 + 时长 + 13.5px 形状 | 1 次注视 |
| 1 | 读那句话：「等你批 Bash」 | **答案就是这句** |

合计 **2 步，0 滚动**。

**但「2 步 vs 16 步」本身还不能证明它是质变——那也可能只是量级。** 三条更硬的证据：

1. **排序这一步从用户手里拿走了。** 旧版从来没有做过排序：用户要自己把 9 个结果按紧急度在心里排一遍，而**在 9 项上做排序需要同时持有 9 项**——这是工作记忆的硬上限，也是「挨个扫一遍」这句话真正的痛苦来源。新版由 `attentionOf`（`layers.js:40-48`，纯函数、可单测、9 条用例覆盖两两组合）做 `alert > error → 同组按最久优先`，行的**纵向位置就是排名**。所以不是「扫 9 个变成扫 3 个」，是「**自己排 9 个变成读一个已经排好的**」。扫 3 个仍然要排，读 3 行不用。
2. **每个注视点承载的信息密度变了。** 旧版把「要不要我管」压进 27px²（0.09%），新版是整行 400×44 都在编码它：彩条（色）+ 灯（形状，13.5px = 旧灯 5.2px 的 **3.4 倍**）+ 名字（600 权重）+ 句子（文字是密度最高的通道）。需求用 95%/0.09% 做的诊断，这一版把那个比例翻了过来。
3. **「没事」这个方向第一次被回答了。** 旧版有没有事长得一模一样，所以「没事」和「我没看」无法区分，他只能一直看。新版 `✓ 没有需要你的事` 是一句**肯定陈述**（`attention.js:30-35`）。需求说这是「第二个方向，现在完全没被设计过」——现在设计了，而且全 idle 时主体只剩 52px、**一个数字都不跳**（层 3 无时长，头部 `bb-pulse` 只在 busy 时开），静置 60 秒真的零变化。

**没解决的，说清楚：**

- **当前实现会在最该准的那 1.5 秒里说反话**（§4.6 的 P0）。一个 1.5 秒的窗口，配上「每 1.5 秒轮询一次」，用户的扫视有实际概率落在里面——而且落在里面的那次，正好是他刚点完审批、最想知道结果的那次。
- **4 件以上时，第 4 个人连名字都没有**（§4.7 的 P1）。「谁最急」这个问题在 4 件以上退化成「有 4 件以上，具体谁不知道」。
- **层 1 内部 3 行之间，只有位置和彩条在区分排名**，没有序号、没有尺寸梯度。读顺序 = 排名，够用，但需要用户知道「上面那条更急」这个规则。头部 `bb-sum-hot`（700 权重）在 `counts.alert > 0` 时替他说了一半。

## 2. 新发现 P0 · chip 嵌在可点行里，点它等于点了那一行

**`attention.js:66-79`。** chip 是 `.bb-attention-row` 的**子节点**，而行本身有 `onClick: () => onOpen(row)`。chip 的 `onClick: () => onExpand?.()` **没有接收事件、没有 `stopPropagation`**（arity = 0，实测）。React 的合成事件照常冒泡。

我按浏览器的事件流手工跑了一遍（shim 不分发事件，所以直接调两个 handler，顺序就是冒泡顺序）：

```
点 chip：  onExpand()  ->  onOpen(数学)        ← 打开了第 3 行那个 Bot 的抽屉
按 Enter： preventDefault -> preventDefault -> onOpen(化学)
```

**用户点「+2」，得到的是「数学」的抽屉。** 抽屉是 `position:absolute; inset:0; z-index:2`，整块面板盖住 —— 所以展开其实发生了，但用户看见的是别人的详情页。按 Esc 关掉才看到 5 行。

为什么 P0 而不是 P1：这个 chip 是 P1-1 的**全部产出**（「让第 4 个人可达」），而它 100% 的激活都先把用户扔进一个不相干的抽屉；鼠标和键盘两条路都中；而且这是新增控件，不是遗留问题。修复是一行。

**修法**（`attention.js:74-77`）：

```js
onClick: event => { event.stopPropagation(); onExpand?.() },
onKeyDown: event => {
  if (event.key === 'Enter' || event.key === ' ') {
    event.preventDefault()
    event.stopPropagation()   // 行的 Enter 处理器否则会打开抽屉
    onExpand?.()
  }
},
'aria-label': expanded
  ? t('attention.collapse')
  : t('attention.overflow').replace('{n}', String(overflow)),
```

`preventDefault` **不够** —— 行的 `onKeyDown` 只看 `event.key`，不看是否已被处理。必须 `stopPropagation`。

**必须配断言**（否则下一个人重构掉 `stopPropagation` 也没人知道）。shim 不分发事件，所以断言机制本身：

```js
let stopped = false, opened = 0
const tree = mount(Body, { ...bodyProps(fiveHot), onOpen: () => { opened += 1 } })
const chip = findAll(tree, n => n.props?.className === 'bb-att-more')[0]
chip.props.onClick({ stopPropagation: () => { stopped = true } })
check(stopped, 'P1-1 the chip stops the click before it reaches the row')
// keyboard 同理，断言 event.stopPropagation 被调用
```

**对照：层 3 的 `+N` 没有这个问题** —— `.bb-idle` 本身没有 `onClick`，`+N` 是名字们的兄弟节点而不是子节点（实测 `idle.props.onClick === undefined`）。所以「照抄层 3 的 `+N`」这句话只说对了一半：抄了结构，没抄「不嵌在可点区域里」这个前提。

## 3. 新发现 P1 · `attExpanded` 粘滞，自愈只自愈了 chip 没自愈状态

`panel.js:157` 的 `attExpanded` 只有点 `−` 才会变回 false。计数掉到 ≤3 时 chip 消失了（`attention.js:44` 的 `chip` 条件），**于是用户再没有 `−` 可点，状态永久留在 true**。

实测（持久 `useState`，直接调 chip 的 onClick）：

```
5 hot 折叠       L1=3  chip="+2" data-expanded=false
点一下           L1=5  chip="−"  data-expanded=true
掉到 2 件        L1=2  chip=(none)          ← 视觉上自愈了
又回到 5 件      L1=5  chip="−"  data-expanded=true   ← 自己又展开了，没人要求
```

**后果不是美观问题，是布局**：320 面板、5 行展开时 `39 + (5×44 + 4×3 + 10) + 24 = 305`，**层 2 只剩 15px**（下限 96）。而这次展开是十分钟前为了另一批 5 个人点开的。

实现者反对我上一轮「单向展开」建议的理由是「单向展开是个用户无法撤销的状态」——这个反对**部分成立**：toggle 确实给了撤销路径。但粘滞是另一种「无法撤销」：用户没有地方表达「我只想展开那一次」。

**修法**（`panel.js` Body 内，两行）：

```js
const hotOver = hot.length > ATTENTION_MAX
useEffect(() => { if (!hotOver) setAttExpanded(false) }, [hotOver])
```

断言：mount → 展开（5 件）→ 掉到 2 件 → 回到 5 件 → **必须是 3 行 + chip**，不是 5 行。

### 关于 toggle 本身：**同意实现者的判断**

我上一轮建议「单向展开」，实现者改成 toggle 并给了理由。理由是成立的：层 1 是 `flex:none`，9 个审批展开就是 242px，会把另两层挤出 320 —— 而层 3 的 `+N` 敢单向，是因为 `.bb-idle[data-expanded]` 被 CSS 限死在 `max-height:44px`（两行）。层 1 没有这个上界。**所以「可撤销」在这里不是偏好，是必需品。** 我撤回原建议。

但 toggle 只解决「能不能撤销」，没解决「上界在哪」。如果要做完整，可以再加一条：展开上限 6 行（`min(hot.length, 6)`），其余交给头部计数 —— 不过这是 P2，不做也能交付。

上一轮那四条仍然有效（等 P0 修完、两个固定视口、420 是默认、必须含六个退化态）。再加三条，都是这次新出现的：

1. **必须导一个「4 件以上需要你」的态，并且真的点一下 `+2`。** 这是 P0 现场；静态 HTML 不点就看不见。
2. **必须导一个「层 1 展开 5 行 + 320 面板」的态**，看层 2 剩 15px 时是什么样子 —— 那是 P1 的最坏情况，也是判断「要不要给展开加上界」的唯一依据。
3. **560×480、3 件需要你、6 个在动**这一张现在是本版的核心卖点（478.86 ≤ 480，余 1.14px）。**请专门导这一张并量一下有没有滚动条** —— 1.14px 的余量是这一版全部高度算术的成败点，而它是唯一需要真实布局引擎才能确认的数字。
